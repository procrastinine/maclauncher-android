# Application locales

The shared Android platform service exposes the original `ILocaleManager` Binder interface through `Context.LOCALE_SERVICE`. Its five methods retain Android's package and user checks, locale lists, system-locale queries and supported-locale configuration overrides. Package identity and permissions use the same authenticated process and package directory as the other platform services.

The complete supplied AOSP `LocaleManagerService`, backup helper, package monitor and shell command remain the service implementation. The host supplies their system-server package configuration boundary through the original `PackageConfigPersister` and `PersisterQueue`. Locale records and supported-locale overrides use Android's original atomic XML stores; delegate and staged backup information use the original device-protected preferences. The backup payload interface retains the original package enumeration and locale serialization. Backup transport availability remains a separate platform service responsibility.

Each application reads its persisted package locales before its component factory and Application are initialized. Later changes use authenticated Binder callbacks in the existing process directory, then the application lifecycle handler and original ResourcesManager configuration dispatch. Application locale overlays retain the system locale fallback. ActivityManager and LocaleManager system-configuration queries continue to expose system locales independently of those overlays.

Package installation, updates, removal and data clearing feed the original package monitor on its own handler. Configuration delivery retires with the process directory; service shutdown removes registrations and drains the original persistence owner. JVM and ART applications use these shared Java service and lifecycle boundaries; their native memory and graphics execution remain separate.
