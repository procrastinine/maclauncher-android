# Application locales

Application locales use Android's original `ILocaleManager` Binder interface, which MacLauncher Android's shared platform service provides through `Context.LOCALE_SERVICE`. The interface's five methods keep Android's package and user checks, locale lists, system-locale queries and supported-locale configuration overrides. Package identity and permissions come from the same authenticated process and package directory as the other platform services.

The service is the complete supplied AOSP `LocaleManagerService` with its backup helper, package monitor and shell command. The host provides the package configuration that these classes normally get from the system server, through the original `PackageConfigPersister` and `PersisterQueue`. Locale records and supported-locale overrides are kept in Android's original atomic XML stores, and delegate and staged backup information in the original device-protected preferences. The backup payload interface keeps the original package enumeration and locale serialization. Whether a backup transport is available is up to a separate platform service.

Each application reads its saved package locales before its component factory and Application are initialized. Later changes arrive through authenticated Binder callbacks in the existing process directory, then go through the application lifecycle handler and the original ResourcesManager configuration dispatch. Application locale overlays fall back to the system locale. ActivityManager and LocaleManager system-configuration queries report the system locales regardless of those overlays.

Package installation, updates, removal and data clearing reach the original package monitor on its own handler. Configuration delivery stops when the process directory shuts down. Service shutdown removes registrations and drains the original persistence queue. JVM and ART applications use these shared Java service and lifecycle classes, while their native memory and graphics execution stay separate.
